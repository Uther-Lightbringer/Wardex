# 性能预算与稳定性设计

> 相关文档：[design-principles.md](./design-principles.md)（红线 R1~R4 的量化依据）· [architecture.md](./architecture.md) · [implementation-plan.md](./implementation-plan.md) · [panels.md](./panels.md) · [features/chat.md](./features/chat.md)

本文档把"极致性能、极少内存、绝对稳定"落成**可验收的预算数字**。与红线同级：实现任何功能前检查是否破坏本文档的某一条预算；验收时逐条核对。

## 1. 总原则

1. **磁盘是唯一真相**：内存里的一切都可从磁盘重建，因此一切都可卸载。
2. **缓存三要素**：任何缓存必须同时声明 上限 / 淘汰策略 / 失效条件，缺一不许存在。
3. **增量全链路**：ACP → chat → 事件 → 前端 → DOM，每一跳只传增量、只改增量。任何一跳退化为全量复制，长输出就会卡（旧版 P1 的教训）。
4. **不可见不工作**：折叠面板、滚出视口的气泡、后台会话，不渲染、不取数、不计时。

## 2. 三层缓存模型

```
┌─ 前端（WebView）──────────────────────────────┐
│ 消息列表虚拟滚动：只渲染视口 ±buffer；markdown 仅 │
│ 回合结束解析一次；图片解码限 1920px；无权威数据副本 │
├─ Rust 内存 ───────────────────────────────────┤
│ 会话索引（仅 meta）常驻；消息模型 LRU≤5；          │
│ 流式缓冲只留增量+尾 2000 字符；payload 截断 64KB   │
├─ 磁盘 ────────────────────────────────────────┤
│ JSONL/JSON；append-only 优先；原子重写             │
└────────────────────────────────────────────────┘
```

## 3. 缓存预算表（三要素强制登记）

| 缓存 | 上限 | 淘汰 | 失效条件 |
|---|---|---|---|
| 消息模型（含 segments） | 5 个会话 | LRU | 会话删除/重开 |
| ACP 子进程 | 20 个 | 停最久未活动 idle（全 busy 允许临时超限） | 会话删除/进程退出 |
| 流式合并缓冲 | 未 flush 增量 + 尾部 2000 字符 | flush 即清 | 回合结束 |
| 工具 payload（内存） | 64KB/条 | 截断（全文只落盘） | — |
| 全文搜索结果 | ≤3 hits/会话 | 代际作废（新查询废掉旧结果任务） | 输入变化 |
| 文件树列表 | 每会话 1 份 | 随会话模型卸载 | 目录 mtime 变化/手动刷新 |
| CLI 探测结果 | 每 provider 1 份 | 显式刷新 | agent 配置变更 |
| 前端气泡 DOM | 视口 ±buffer | 虚拟滚动卸载 | — |
| 面板数据（git/diff/db 等） | 展开的面板各 1 份 | 折叠即弃 | 见 [panels.md](./panels.md) 的 refreshOn |
| 后台任务（tasks 面板） | 每会话 1 份，条数有限 | 会话模型卸载即弃 | `acp://subagent` 事件（`task_id:` 应答 + TaskList/TaskOutput 更新）增量刷新；会话切换用 `get_subagents` 快照重建 |
| 图片解码 | 1920px 边长 | 解码即缩放 | — |

新增缓存时**必须在此表登记一行**。

## 4. 写路径预算

- 流式期间**零磁盘 I/O**；回合结束一次 `messages.jsonl` 原子重写（tmp + rename）。
- `meta.json` 更新防抖合并（同回合内多次字段变更只写一次）。
- 崩溃安全：JSONL 追加写最多丢最后半行（加载容错跳过坏行）；原子重写不存在半写文件。

## 5. 性能硬规

- **零拷贝优先**：chunk 载荷用移动语义/`Arc<str>`；禁止"定时把全文复制一遍"的任何变体。
- **后台让路**：搜索、文件树扫描在 tokio 任务/阻塞池执行，配代际作废，不堵 UI 命令；IPC 高频事件维持 50ms 合并节奏（积压 >64KB 升 250ms）。
- **解析懒惰化**：markdown/JSON 美化/语法高亮只在可见且需要时执行，一次性结果可缓存（随内容失效）。

## 6. 稳定性五道防线

1. **故障隔离**：每个会话 runtime 独立 tokio task；单 CLI 崩溃/协议错乱只影响该会话，收敛为气泡内"回合失败"，应用不崩。
2. **超时全覆盖**：spawn 8s、probe 4s、cancel 2.5s 强杀、guideAt 800ms——所有外部交互无例外。
3. **背压有界**：发送队列 ≤10、附件 ≤6、流式缓冲超限降频；任何队列/缓冲禁止无界增长。
4. **写盘崩溃安全**：见 §4；启动时将残留 `pending` 消息标记 `interrupted`。
5. **生产路径零 `unwrap`/`expect`**（clippy 强制）；内存看门狗超阈值（带回滞）→ 主动卸载空闲会话模型 + 前端横幅。

## 7. 验收指标（阶段 4 核对）

- 旧版卡死场景（长 thinking 回复、含大文件内容的工具调用）流畅：流式期间 UI 帧率不掉、内存不随输出长度线性增长。
- 连续打开 10 个会话后，内存增量 ≈ 5 个会话模型（LRU 生效可证）。
- 强杀任一 CLI 进程：仅对应会话报错，其余会话与应用无恙。
- 强杀应用自身：重开后最后一条流式消息为 interrupted，数据文件无损坏。
